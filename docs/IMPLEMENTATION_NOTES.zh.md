## 1. `chain_public_key`，以及冻结这条线实际落在哪里

**这一条的两半现在都已写进规范**——`chain_public_key` 列在 `PROTOCOL.zh.md` §4 里，§4.1/§4.2 画出了冻结/运营的边界。这条笔记记录的是**为什么**，因为光看字段列表看不出这个推理。

### 1a. 光有哈希什么也验证不了

§4 最初只列了 `chain_hash`，没有公钥。那不足以验证任何东西。`drand-client` 是把两者一起检查的：

```js
// node_modules/drand-client/http-caching-chain.js
function isValidInfo(chainInfo, validParams) {
  return chainInfo.hash === validParams.chainHash && chainInfo.public_key === validParams.publicKey;
}
```

只传 `chainHash` 的话，`validParams.publicKey` 就是 `undefined`，于是这个比较对任何一条真实的链都失败。陷阱在于接下来会发生什么：这个错误看起来像是配置错误，而显而易见的「修法」是干脆把 `chainVerificationParams` 整个去掉——那就静默地关掉了链验证。到那一步，一个有敌意的、或者仅仅是填错了的 `drand_api` 就能供出一条伪造的链，而浏览器和开奖任务都会相信它。

所以 `protocol.json` 里带着 `chain_public_key`，`server/config.js` 在缺它时拒绝启动（并且拒绝一个 64 字符的值，因为那是链哈希的形状而不是群公钥的），`server/tlock.js` 和 `client/seal.js` 两边都把两个值钉死。对 quicknet，2026-09-09 对着 `https://api.drand.sh/<chain_hash>/info` 核对过：

```
chain_hash       52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971
chain_public_key 83cf0f2896adee7eb8b5f01fcad3912212c437e0073e911fb90022d3e760183c8c4b450b6a0a6c3ac6a5776a2d1064510d1fec758c921cc22b0e17e63aaf4bcb5ed66304de9cf809bd274ca73bab4af5a6e9c76a4bc09e76eae8991ef5ece45a
scheme           bls-unchained-g1-rfc9380      period 3s
```

`tools/pick-round.js --in 72h --write` 会把这些全部填好，并且把 `target_round` 和 `submission_cutoff_utc` 一起设定，让它们不可能互相矛盾。它不再自带一份 quicknet 哈希的副本：链是什么，取决于 `protocol.json` 冻结成什么，而工具里的第二份副本只是它可能出错的第二个地方。

### 1b. 同一个论证说明 `drand_api` **绝不能**被冻结

把哈希和公钥钉死，恰恰正是让端点可以松着的原因。一个被换掉的或者有敌意的 `drand_api` 没法偷换一条链——`isValidInfo` 会拒绝它——所以它只能大声失败。这意味着它通不过那条决定冻结与否的判据：

> 在提交开放之后改动这个值，是否可能改变结果，或者让某人得以操纵结果？

硬要冻结它只会让这一轮严格地更糟。一个 drand 镜像在窗口期中途挂掉是一件与结果无关的普通运维事件，而在 `drand_api` 被冻结的情况下，协议内唯一的补救就是作废本轮。更糟的是，现实中的结果并不是一次作废：而是组织者编辑一个已打 tag 的文件，然后告诉所有人没事——而这恰恰是冻结存在的目的所要防止的那个习惯。一个覆盖了人们有正当理由去改的东西的冻结，只会教会所有人：冻结的文件是会被改的。

**结论。** `protocol.json` 只放那些可能改变或操纵结果的东西。其余一切都搬到了 `data/runtime.json`（默认值放在 `server/runtime.js` 里，文件本身可选且被 gitignore）：drand 端点和镜像列表、Pantheon 基础 URL 和 Twirp 命名、SSE 心跳、status 轮询间隔、会话 TTL、限流。一旦 `protocol.json` 里出现运营配置键，`config.js` **拒绝启动**，并指出它本该待的地方——这个划分只有在不可能被悄悄侵蚀的前提下才值钱。

由同一条原则——一个冻结的值必须恰好存在于一个地方——还引出两处连带清理：

- **浏览器 bundle 里不给任何冻结值兜底。** `Void.jsx` 曾经渲染 `quorum ?? 8` 和 `total_slots ?? 12`，`Submit.jsx` 和 `seal.js` 曾用 `user_input_max ?? 255`。那些是被打了 tag 的值的占位副本，可以随意说出一条这场抽签实际并未依据的规则。它们现在来自 `/api/status`，否则那一屏干脆不渲染。
- **单字节的边界来自 `generate.js`。** `local_id` 落在 `1..255`、`user_input_max <= 255`，是 §7 字节编码的推论，不是偏好，所以 `generate.js` 导出 `ENCODING_LIMITS`，`config.js` 对着它校验，而不是把字面量再抄一遍。

## 2. `results.json` 只装 `generate.js` 算出来的东西

§4 最初把 `pantheon_sync` 放在 `results.json` 里，而 RUNBOOK 第 A5 步要求仅凭 `results.json` 就能重算一次已完成的抽签并逐字节一致。两者不能同时成立。e2e 测试第一次运行就抓到了这一点，而那正是它存在的意义。

`pantheon_sync` 有三重不可复算，而第三个理由才是定案的那个：

| | 为什么它算不出来 |
|---|---|
| `at` | 一个墙钟时间戳，而 `generate.js` 不允许读时钟 |
| `status`、`attempts`、`error` | 一次对另一个系统的网络调用的结果 |
| 这个字段本身 | 它记录的是 `results.json` 被写出**之后**发生的事 |

一个文件不能对它算不出来的值做出逐字节一致的主张。本实现的第一版把这个字段从比对里挖出去，并在输出里点名说明，那是诚实的，但留下了一个带脚注的验证——而脚注正是没人会读的那部分。

**结论。** 同步结果搬到了 `events/sync.json`。`results.json` 现在恰好在同步运行之前写出一次，`--verify` 逐字节比对它的每一个字节，不挑出任何东西。`GET /api/result` 为 UI 把结果、统计和同步重新拼在一起，因为那是一个视图，不是一份产物。

`excluded_local_ids` 走的是相反方向，而且是刻意的。一份打不开的提交不是一份贡献（第 5 条），所以**谁被排除了**是「谁参与了」这个答案的一部分，必须在主张之内，而不是注解在主张之外。`generate.js` 现在把这份名单作为输入接收并校验它：每个 id 都在名册里、没有一个同时是参与者、每个都带理由，以规范顺序输出，并且空列表也显式写出来，这样「没有人被排除」和「这个字段被丢掉了」不会长得一样。

### 2a. 逐字节比对仍然看不见什么，以及什么能看见

`--verify` 是**从文件所列出的载荷**重算的。所以一个把某位选手同时从 `revealed` 和 `excluded_local_ids` 里漏掉的 `results.json` 能完美复现。有一个测试就是专门构造这样一个文件并确认它是自洽的，因为这个局限值得钉死，而不是指望没人注意到。

`events/snapshot.json` 是堵上它的东西。它在截止时刻写出——此时信标尚不存在，所以此时还没人能知道漏掉谁有用——并且和密文一起被公开镜像。它里面的每一个 id 都必须恰好出现在那两份名单之一里：

```
OK    results.json reproduces byte for byte — the whole file, no fields set aside
OK    12 submitted at the cutoff = 10 participating + 2 excluded
```

`--verify` 会在 `results.json` 旁边找那份快照并自动执行点名核对。找不到时它会用一种不可能被误认为通过的措辞说出来，而 e2e 运行会断言这项检查确实发生了，而不仅仅是逐字节比对发生了。开奖任务还会在结果**之前**先镜像快照，所以读者绝不会遇到「结果已发布、但审计它所需的文件还没有」的情况。

于是有两个互相独立的主张，不应该被混为一谈：

- **抽签是从这些载荷推出来的**——逐字节比对
- **这些载荷就是所有提交过的人**——点名核对，再加上「每一份密文在到达时就已公开并由第三方打上时间戳」这一事实

## 3. §7 留白的选择，现在钉死了

§7 警告说，把字节编码钉死和把算法钉死同等重要。以下是被钉死的内容，而且由校验强制，不是靠约定：

```
SEP = 0x1F

contribution_i = SHA256(DOMAIN ‖SEP‖ "contrib" ‖SEP‖ u8(local_id) ‖SEP‖ u8(user_input)
                        ‖SEP‖ nonce16 ‖SEP‖ ascii(client_timestamp))
R              = 全部贡献的异或，256 位，不截断
seed           = SHA256(DOMAIN ‖SEP‖ "seed" ‖SEP‖ R ‖SEP‖ hexdecode(signature)
                        ‖SEP‖ 每个参与者的 u8(local_id)，升序)
```

- **签名是十六进制解码后拼进去的，不是作为文本追加的**，这样大小写不同的十六进制就不会从同一个信标值产生两个不同的种子。
- **单射性是挣来的，不是假定的。** 每个字段要么是定宽的（`local_id`、`user_input`、nonce、`R`），要么被校验为不含 `0x1F`（`DOMAIN`、时间戳），而唯一一个数量可变的字段（那些 local id）放在最后。一个可能夹带分隔符的字段会被**拒绝**，不是被转义——含有 `0x1F` 的 `seed_domain_separation` 在启动时失败，而时间戳必须匹配一套严格的 ISO-8601 文法。
- **CSPRNG：** `block(i) = SHA256(seed ‖ uint32be(i))`，依次拼接。
- **均匀抽取：** 读 4 个大端字节，大于等于 `floor(2³²/n)·n` 就拒绝，然后取余——§7 说的「拒绝采样，不是取模」。
- **Fisher-Yates：** 降序进行，遍历名册里按升序排列的 local id。
- **π 的方向：** `permutation[k]` 是**坐在抽象点 k 上的 local_id**。`results.json` 里用一个 `permutation_note` 把这句话写出来，任何验证者都不必猜。
- **序列化：** `JSON.stringify(x, null, 2)` 加一个结尾换行。

`tools/verify_contribution.py` 把这一切**用另一种语言、依据上面那段散文而不是依据 `generate.js`** 重新推导了一遍。如果编码有歧义，两者就会对不上；单元测试里它们互相校验一次，e2e 运行里再校验一次。那就是 RUNBOOK A5 真正的内容。

## 4. 密文在提交时就检查，不是只在开奖时检查

§6 让中继盲目接受密文，就「它能读到什么」而言这是对的——它解不了密。但它能读 age 的 recipient stanza，那是明文，从而确认这份密文是封给冻结的那条链和那一轮的。

这件事要紧，是因为 §8 数的是**提交**，不是**有效的**提交。一份锁在另一轮上的密文会躺在快照里、占掉一个门槛名额，然后只在开奖时失败——那已经是截止之后，那位选手再也没法重新提交，而这一轮可能已经不足八人了。`server/ciphertext.js` 在门口就拒绝它，在那个时候，补救办法不过是刷新一下页面。

## 5. 万一某份提交打不开会怎样（§8 对此沉默）

第 4 条堵上了现实中的那条路径，但任务仍然需要一个确定性的答案。

**实现采用的规则：** 一份解不开、或者载荷格式不对的提交，不是一份贡献。它被排除在 `R` 之外，然后门槛按实际打开的份数重新检查。仍然 ≥ 8，抽签继续，被排除者公布在 `results.json` 里；低于 8，这一轮按 §8 作废，和其他任何门槛不足的情形一样，`events/void.json` 记录哪些失败了以及为什么。

把一团打不开的东西计入门槛，会让一个人用垃圾数据强行凑出一次开奖。这条规则是确定性的，不给组织者留任何裁量空间，而那正是 §8 在意的性质。

## 6. 已发布的 `results.json` 在任何地方都压过数据库

`phaseOf` 在别的任何东西之前先查 `results.json`。没有这一条，在一次已完成的抽签之后把服务器恢复到一个全新数据库上，这一轮会被报成**作废**——一张过了截止时刻仍然空着的提交表，和一次门槛不足是分辨不出来的。告诉选手一场已完成、已公布的抽签作废了，是可选答案里最糟的那个错，而 RUNBOOK 明确写着 `results.json` 权威、SQLite 状态可弃。

这条原则曾经被写出来但并没有被真正实现，有两处，都已修复：

- **`phaseOf` 先查的是持久化的 phase。** 所以那道 `results.json` 守卫只在数据库里**完全没有** phase 时才生效。一旦有什么东西写进了 `void`，答案就永远是作废，而已发布的结果就摆在旁边。现在文件在持久化的键之前被检查，这也正是它周围那段注释一直声称的行为。
- **`run()` 根本没用 `phaseOf`。** 它直接读持久化的键，所以在一个全新数据库上，定时任务径直绕过守卫、对一张空的提交表做快照、发现它低于门槛，于是**把 `events/void.json` 发布到一次已完成的抽签之上**——过程中还把它镜像进了仓库。任务每分钟跑一次，所以只要丢一次 `var/`，这件事就会自己发生。`run()` 现在通过 `phaseOf` 推导自己的状态，并让数据库与文件对齐。`test/resume.test.js` 把它钉住了。

## 6a. 同步是开奖之后唯一允许悬而未决的步骤

同步在 `results.json` 已发布、phase 已经是 `done` 之后运行，所以中途一次崩溃或重启会让它没做完，而且没有任何东西会把它捡起来。现在结果有了自己的文件（第 2 条），「它跑过没有？」就是一个磁盘上有答案的问题，定时器会把它续上：写 prescript 再读回来是幂等的，而且碰不到抽签。

它**只在从未记录过任何结果时**续做。一次被记录的失败是一次已完成的尝试，带着一份成文的人工补救办法（RUNBOOK 第 15 步）；每五分钟永远重试一次只会把那份补救埋在镜像噪音之下，并且和一个已经手工把 prescript 粘进去的运营者对着干。

## 6b. §8 的补救办法需要一些当时并不存在的代码

§8 说，一次作废之后要跟上一个新的 `target_round` 和一批全新的提交。当时没有任何东西实现了这件事，而且这个缺口不是表面功夫。在一次作废加重新冻结之后探测状态：

```
phaseOf says: void
phaseOf on a FRESH database: void
old submissions still counted: 1,2,3,4,5,6,7
player 1 resubmitting -> {"stored":false,"reason":"already_submitted"}
```

三条互相独立的死路：选手永远看到「作废」；绑定在已过期轮次上的密文仍然计入新的门槛；而且谁也没法重新提交。

**结论。** 一次运行现在是一串「尝试」。`server/rounds.js` 在一次尝试被判作废的那一刻把它归档，`tools/new-round.js` 开启下一次。

重点是归档，不是重置。「不到八人提交」是一个主张，而且恰恰是一个想在看清来了谁之后再来一次的组织者会做出的主张。所以证据是被公布而不是被清掉的：按收到原样保存的每一份密文、截止时取的提交名单、通知，以及**那次尝试所依据的 `protocol.json` 和 `roster.json`**，配一份 SHA-256 摘要的 `manifest.json`，全部镜像出去，让第三方给它打上时间戳。

把 `protocol.json` 归档是让其余部分可用的那一环。下一次尝试会用新的 `target_round` 覆盖它；没有这份副本，归档里的密文就会指向一条链和一个轮次，而仓库里再无任何记录，证据也就打不开了。作废那一轮的信标无论如何三秒后就会落地，所以把 `tools/decrypt-submissions.js` 指向归档，它会打开每一份密文并数一遍——作废于是变成可核验的，而不是被凭信接受的。

重置被刻意做得难以误用。它会拒绝，除非这一轮确实被判了作废、它的归档逐字节验证通过、`protocol.json` 里已经写着一个更晚的轮次且截止时刻在未来、并且不存在 `results.json`。先重新冻结，再重置，这样绝不会出现一个开着却没有公布过目标的轮次。因为已提交的人选而重启一个仅仅是**开着**的轮次，正是 §8 存在的目的所要消除的那个可操纵步骤，而重置不会去做它。

## 6c. 运营的那一半：一个面板和一条冻结命令

RUNBOOK 的 B、C、D 三节是散文，其中三步根本没有可执行它们的东西。第 13 步说要催还没封存数字的人；第 15 步说要确认同步生效；`PANTHEON-INTEGRATION.zh.md` §4 说同步失败应当「在管理视图里暴露出来」——而当时根本没有管理视图。冻结本身则是十几个手工动作，在正日子、时间压力之下执行一次。

**`server/admin.js`** 就是那个面板，位于 `/admin`，由 `ADMIN_TOKEN` 把门。有两个决定塑造了它：

- **只读。** §9 让开奖任务离开 HTTP，这样外人能戳到的东西都不能触发、重试或改变开奖的时机。这里放一个按钮就会把这一点拱手让出，换来一个没人需要的便利：运营者在跑 `tools/new-round.js` 的时候本来就在那台机器上。非 GET 方法回答 405，并且有一个测试这么说。
- **不属于冻结的 bundle。** `public/app.js` 被哈希钉死，因为它处理选手的明文数字。这里的东西都不处理，而把它折进去会为了一个与抽签无关的理由改变那个冻结哈希。所以它是一个服务端渲染的字符串，没有构建步骤，也没有依赖。

它显示每位选手**什么时候**提交，绝不显示**提交了什么**——和其他地方同一条规则，而这里是整个代码库里最容易不小心破坏它的地方，因为它是唯一一块职责就是「给组织者看得比选手多」的屏幕。有一个测试会把数据库里的每一份密文拿出来，断言它们没有一份出现在页面或 `/admin/data.json` 里。

起飞前面板用三个级别而不是两个，因为最要紧的那两种状态单独看既不是绿也不是红：跑在桩上、或者关着镜像，在笔记本上是正确的，在生产环境里是灾难性的。第一版草稿曾经在一行详情「STUB —— 会授权桩认识的任何人」旁边渲染出「ok」，那比根本没有这一行更糟。

**`tools/freeze.js`** 把 RUNBOOK 第 8-11 步合成了一条命令。它把名册从 Pantheon 读回来，并拒绝冻结任何只会在之后才浮现的问题：参赛人数不等于 `total_slots`、某位选手没有可用的 `local_id`、同一个账号登记了两次。`local_id` 那一条最尖锐——它会卡住座位表同步，而同步在开奖之后运行，那时什么都改不了。

它还跑那些以前只靠记性的检查：重新推导模板已证明的不变量、**从源码重建**浏览器 bundle 并与已提交的那份**比对**、跑单元测试。这个重建必须发生在冻结的时候，别的地方都不行：它需要 esbuild，而 VPS 上没有，所以 VPS 跑的是 `--verify-hash`，那只比对已提交的 bundle 和它已提交的哈希，因此没法告诉你那个哈希是不是从另一份源码算出来的。

不传 `--tag <name>` 时它不碰 git。不传的话，命令会打印 `git add` 和 `git tag` 两行然后退出。

## 6d. 检出里的字节不是被提交的那些字节

这是在一个用完即弃的克隆里测试 `tools/freeze.js` 时发现的：同样的源码，`build-client.js --check` 在那里失败，在工作树里通过。

| | 字节数 | CR | 摘要 |
|---|---|---|---|
| git blob | 347717 | 0 | `52c9ed…`（与 `app.js.sha256` 一致） |
| 全新克隆的检出 | 347738 | 21 | `89fd10…` |

`core.autocrlf=true`——Windows 的默认设置——在检出时改写行尾。仓库当时没有 `.gitattributes`，所以每一份按字节钉死的产物从克隆里出来时字节都不同，摘要也就不同。

这不是表面问题。`--verify-hash` 是 `deploy/README.zh.md` 让 VPS 跑的那条命令，也是一个参与者用来确认「处理了我的数字的那份代码就是被打了 tag 的那份代码」的东西。在一份全新的 Windows 克隆上它失败了，而那里的失败读起来像被篡改，而不像一个行尾设置。管理面板为 `protocol.json`、`roster.json` 和 `generate.js` 显示的摘要也有同样的问题。

**结论。** `.gitattributes` 设了 `* text=auto eol=lf`，并把按字节钉死的产物标为 `-text`，那会完全关掉转换，所以任何本地 `core.autocrlf` 都无法把它重新引入。重新克隆验证过：347717 字节，没有 CR，摘要一致。`test/checkout.test.js` 守着它——它断言这些规则存在、已提交的 bundle 哈希等于它已提交的摘要、并且没有任何按字节钉死的产物含有 CR。

这里的一般教训值得留着：一个从未从全新克隆检查过的可复现性主张，就是没有被检查过。本项目的每一项验证都是在写出这些文件的那棵树里通过的，而那恰恰是这个 bug 唯一不可能出现的地方。所以这项检查现在是某个人的职责而不是没人的职责：`.github/workflows/reproducibility.yml` 在一份全新克隆上跑 `--verify-hash`、`--check`、模板不变量和单元测试，在 Linux 上跑一遍，在刻意恢复了 `core.autocrlf=true` 的 Windows 上再跑一遍。在那个分支上删掉 `.gitattributes` 能精确复现这次失败——347738 字节、21 个 CR、摘要 `89fd10…`、两个红色测试——而这正是这个 job 值得它花掉的那一分钟的原因。

## 6e. 排练由人来执行的那一半

RUNBOOK 的 A 节有 `test/e2e.js`。B、C、D 三节——快照名册、选轮次、冻结、打 tag、催还没交的人、确认开奖跑了并且同步生效了——什么都没有，而它们正是由一个人在正日子、时间压力之下执行一次的那一半。`tools/rehearse.js` 执行它们：一个从工作树建起来的用完即弃的 git 仓库，Pantheon 桩指向一份仓库没见过的报名名单，以及一个四分钟之后的真实 drand 轮次。命令是真命令，服务器是它自己的进程，封存是真的 tlock，开奖任务像 cron 跑它那样独立运行，提交和 tag 都是真的。

它在头两遍就找出了两件事，而且都在最要紧的那一步里：

- **`tools/freeze.js` 根本没法执行第 10 步。** 从 Pantheon 里写出 `data/roster.json` 就是那一步本身，而这条命令先加载完整配置——而那需要一份有效的 `data/roster.json`。第一次冻结时它就停在「复制 .example 文件，然后自己填」：十二行手打，而这恰恰是这个工具存在的目的所要消除的东西，发生在一个 `person_id` 打错就会把某人锁在抽签之外的时刻。`load({ rosterOptional: true })` 现在是唯一的例外，而且只给这条命令用；其他一切仍然把缺失的名册当作启动失败。
- **一次被拒绝的冻结照样写了名册。** `snapshotRoster` 报告报名数据哪里不对，却仍然返回它读到的内容，于是拒绝信息以红色打印出来的同时，`data/roster.json` 出现在了磁盘上，内容是用刚刚被拒绝的那份报名名单建的。下一次运行就会发现一个原本不该存在的文件，并对着它比对。

这两件事和 §6d 里的 CRLF bug 是同一个形状：一个只被写它的人、在唯一能工作的那种布置下执行过的步骤。RUNBOOK 里那几步的顺序也是错的——冻结会拒绝 `target_round` 为 0 的情况，所以选轮次必须排在前面，而它当时写在后面。

排练没有覆盖的，正是 §7 覆盖的那些：Pantheon 是桩，没有浏览器去驱动那份冻结的 bundle，镜像是关的。它会断言面板把这些都说出来了。

## 6f. Pantheon 客户端，对着真实的 Pantheon

§7 曾经说这个 Twirp 客户端从未见过它为之而写的那个东西。现在它见过了：WSL 2 下 Docker 里的 Pantheon `cdda3fc`，而且是通过 `server/pantheon.js` 本身驱动的，不是通过 curl。

它的六条假设是错的。没有一条自己报警：

| | 当初写的 | 实际的 |
|---|---|---|
| 路径 | `/twirp/{service}/{method}` | `/v2/{service}/{method}` |
| 服务 | `frey.Frey`、`mimir.Mimir` | `common.Frey`、`common.Mimir` |
| 端口 | Frey 4001、Mimir 4002 | Mimir 4001、Frey 4004 |
| 响应 | snake_case | lowerCamelCase |
| 密码错误 | `{auth_success: false}` | HTTP 400 `invalid_argument` |
| 管理员作用域 | 两个头 | 三个 —— 还要 `X-Current-Event-Id` |

有意思的是后三条。

**每一个响应字段都返回了 undefined。** protobuf JSON 输出的是 lowerCamelCase，所以在一份每位选手都有 local id 的名册上，`p.local_id` 永远是 `undefined`。这个失败模式是可以挺过去的——`tools/freeze.js` 会拒绝冻结一份没有人有 local id 的名册——但那只是因为那道拒绝存在。同样的 bug 出现在 `getPrescript` 里，会把 `next_session_index` 读成 0，然后悄悄重写第 1 节。

**登录门禁回答的是另一个问题。** Frey 不会把凭证不对报成 `false`；它抛出 400 `invalid_argument` "Password check failed"。而 `server/server.js` 捕获 `verifyToken` 的异常之后返回的是 **503「现在连不上 Pantheon」**。于是每一次打错密码，都会在十二个人同时登录的那一天告诉他们服务器坏了，而 UI-SPEC §3 要求那两种拒绝必须可区分的规定，就这样被静默地违反了。现在拒绝类状态码被当作拒绝读；5xx 和 429 仍然抛出。

**而且默认值是 `return true`。** 老客户端在响应里既找不到 `authorized` 也找不到 `success` 时，返回 true。对着这个 Frey 这一分支到不了——一个错的 token 永远不会换来 200——但它离「授权所有人」只差一个部署。取代它的规则来自 protobuf 的 JSON 映射而不是猜测：一个为 true 的 bool 总是被序列化，一个为 false 的总是被省略，所以 `authSuccess === true` 就是完整的判据，而一份读不懂的响应体就是拒绝。

为了查出这些而把一个实例搭起来花了大约一小时，其中五个障碍记录在 `PANTHEON-INTEGRATION.zh.md` §6 里，因为它们在 Pantheon 的文档里一个都没有。最尖锐的那个：`CreateEvent` 在一个 club 类型的活动上接受 `is_prescripted: true`，报告成功，如实存下 wind shuffle 模式，然后把 `is_prescripted` 设成 0——只有 tournament 才能被 prescripted。唯一可见的症状是名册回来时没有任何 local id。

## 7. Pantheon 边界，以及哪些**没有**被验证

应用需要从 Pantheon 得到的一切都经过 `server/pantheon.js` 里的一个接口，有两种实现：

- **`TwirpPantheon`** —— 真实客户端，按 `PANTHEON-INTEGRATION.zh.md` §5 里的方法名和消息形状写成。
- **`StubPantheon`** —— 一个契约相同的进程内假实现，测试和 `PANTHEON_MODE=stub` 用的就是它。

> **本节写在 §6f 之前，其第一段已被 §6f 取代。** `TwirpPantheon` 此后已经对着一个真实 Pantheon（`cdda3fc`，WSL 2 下的 Docker）运行过，RUNBOOK 第 A2、A3 和 A6 步对着它都通过了——包括把 prescript 读回来、逐个风位比对座位，而那正是 `PANTHEON-INTEGRATION.zh.md` 称为最容易悄无声息出错的那项检查。客户端的六条假设是错的，没有一条自己报警；§6f 把它们列了出来。
>
> 仍然悬而未决的那一项范围更窄，而且**没有**被那次验证关掉：**你实际部署的那个实例**。`PANTHEON-INTEGRATION.zh.md` §5.1 是关于某一个部署的某一个 commit 的事实，而 Pantheon 在演进。

这在实践中意味着：Twirp 路径模板、服务名和基础 URL 全都是可配置的（`runtime.json` → `pantheon`，因为 Pantheon 住在哪里影响不了抽签），所以漂移是一次配置改动而不是代码改动——而 §6f 那六处修正需要的恰恰就是这个。同步被允许**写**什么则保持冻结：`wind_shuffle_mode` 在 `protocol.json` 里，因为任何其他取值都会静默地丢掉模板保证的大部分东西。

一旦 `wind_shuffle_mode` 不是 `WIND_SHUFFLE_MODE_PRESCRIPTED`，`config.js` 就拒绝启动，因为任何其他取值都会静默丢掉模板为之优化的风位平衡和上下家平衡。

## 8. 一条仅限开发的登录路径

§2 让浏览器直接向 Frey 认证，所以这个应用从不接触 Pantheon 密码。那是真正的路径，没有改变。

在没有 Frey 可连的情况下，登录阶段根本没法被构建或检验，所以桩暴露了 `POST /api/dev-authorize`，它把一个 `person_id` 解析成桩里的 token。它**只在** Pantheon 适配器是桩的时候存在，并且在 `NODE_ENV=production` 下返回 404——一个接受密码的端点出现在真实部署上，恰恰是 §2 写出来要防止的事。有一个测试断言它在生产环境下不存在。

## 9. 更小的一些决定

- **浏览器 bundle 是随仓库带的，不是从 CDN 来的。** 提交阶段是选手明文数字唯一存在的地方，所以跑在那里的代码属于冻结范围。`public/app.js` 和 `public/app.css` 带着一个合并的 SHA-256 一起提交；`--check` 重建并比对，`--verify-hash` 只比对已提交的哈希且不需要任何依赖，而后者正是 VPS 跑的（部署用 `npm ci --omit=dev`，esbuild 是 devDependency）。
- **任何人重新生成这个 bundle 时会被咬的两件事：** tlock-js 0.9.0 是 CommonJS，所以对它 `export *` 得到的是一个**空**模块——要按名字重新导出；以及 `Buffer` 这个全局必须从入口点所 *import* 的某个模块里装上，不能在入口点的函数体里赋值，因为模块体是在所有 import 求值之后才运行的。
- **多个 drand 镜像。** `server/drand.js` 查询每一个配置的镜像，一旦有两个对目标轮次的签名意见不一致就**拒绝开奖**。一个镜像挂了没关系；两个互相矛盾是一次「停下所有事」的事件。这份列表是运营配置（`runtime.json`），而加载器总是把 `drand.api` 折进去——对着一组和抽签实际使用的端点不同的端点做一致性检查，等于在检查错误的东西。
- **快照只持久化一次**，在任务过了截止时刻的第一次运行时写下，之后再不重取——所以在一次 drand 故障之后重跑，不可能捡起一份迟到的提交。
- **`generate.js` 自己强制门槛**，没有任何覆盖开关，所以这条规则没法靠手工跑脚本绕过去。
- **用 `node:sqlite`** 而不是 `better-sqlite3`：它随 Node 一起发布，所以运行时依赖树恰好是一个包（`tlock-js`），而且 VPS 上没有本地编译。
- **会话以哈希形式存储**，所以一份数据库导出得不到任何可用的 cookie。
- **统计在服务端计算**（`server/stats.js`），并独立地复现模板已证明的不变量——66 对、55 对完美、三位选手是 5-3-3。如果它们哪天和 `tools/verify_template.py` 对不上，展示给选手的数字就会和我们邀请参与者去跑的那个验证器互相矛盾，所以有测试把两边钉在同一组数字上。

## 6g. 三个从来没被测过的模块

一个通过测试的数量说明不了它们指向哪里。有三个模块一个自己的测试都没有，而每一个被跳过的理由，恰恰就是每一个之所以重要的理由。

**`server/ciphertext.js`** 是通往归档的那扇门：它放进来的一切都会被写进 `events/submissions/` 并镜像到一个公开仓库。它有九种拒绝，其中一种被测过。没被测的那些并不冷僻——一份锁在另一轮上的密文，正是 §8 判一轮作废之后、某位选手从一个过期页面提交时会产生的东西。那一份在门口就被拒绝，因为在截止之后它已经被计入门槛而且无法重新提交。现在有十五个测试，每条规则一个，包括「链在轮次之前被检查」：两者可能同时出错，而链这一项的补救办法不是「刷新再试」。

**`server/mirror.js`** 承载的公平性论证比其他任何文件都多——密文在到达时就是公开的并由第三方打上时间戳，这正是阻止组织者在看到结果之后丢掉一份不合意的密文的东西。它当初以「需要一个真的 PAT」为由被跳过，而那只对 GitHub 那一次往返本身成立。决定一份密文是否到达 GitHub 的每一样东西都是队列、重试和放弃规则，而 `fetch` 是一个测试可以替换掉的全局。现在有十四个测试覆盖它们，包括一个永久失败的文件在五次尝试之后被放弃，而不是把排在它后面的每一份密文都搁浅。

写这些测试时暴露出来的是测试自己的一个毛病而不是模块的，值得记下来，因为它是那种会「通过」的毛病：`enqueue()` 会启动一次 flush 并且刻意不返回它，所以一个只 await 了 `drain()` 的测试会留下一个还在跑的 flush，等桩被放回去之后，它就打到了真的 api.github.com 上。那个文件跑了 103 秒，而且发出了对外请求。现在每一个这样的测试都以一个 `settle()` 辅助函数收尾，跑四秒。

**`server/events.js`** 是唯一能把一个完成的结果送到一个打开着的页面上的东西，因为开奖是由另一个进程执行的（§4.3）。它只有 content type 被测过，别的都没有。现在有十五个测试覆盖：对一个在两次广播之间到达的流的重放、对相同载荷的抑制、心跳随第一个客户端启动并随最后一个停止，以及往一个已经消失的 socket 写数据时丢掉那个客户端而不是在定时器内部抛出异常。

## 6h. 限流器的作用域是代理，不是选手

`RateLimiter` 按 `req.socket.remoteAddress` 取键，这对一台直面网络的服务器是对的，对这一台毫无意义：§10 在前面放了一个反向代理，所以每个请求都来自 127.0.0.1，于是「每分钟三十次」变成了十二个人共享的一份限额。没有任何东西失败；限额只是比预期小了三十倍，而这件事第一次露头的方式，会是几位选手一起登录时被告知等一分钟。

修法不是去读 `X-Forwarded-For`——任何调用方都能发这个头，而一台前面什么都没有的服务器于是会给每一个编造出来的地址发一份限额。修法是 `runtime.json` 里的 `server.trust_proxy`，默认关闭，打开时取**最右边**那一项。`deploy/` 里两个代理构造这个头的方式都是「客户端发来的东西，然后我们实际看到的地址」，所以真相在右边，伪造的前缀坐在它左边。这是对着 nginx 1.28 确认的而不是假定的：一个发 `1.2.3.4` 的客户端到达时是 `1.2.3.4, <它的真实地址>`，一个发两项的到达时有三项。测试的第一版编码的是相反的信念——以为代理追加的是**它自己**——然后失败了，而那是一个测试出错时有用的方向。

## 6i. 给提交名单打时间戳，而不引入一整棵依赖树

`PROTOCOL.zh.md` §9 需要截止时取的那份名单被组织者够不着的某个人打上时间戳。OpenTimestamps 就是这个东西：一个锚进比特币区块的哈希，而没人能挪动一个区块。

官方的 JavaScript 客户端能做到。它的依赖是 web3、bitcore-lib、一个需要编译器的 keccak 绑定，以及已废弃的 `request`——十四个传递依赖包，而这台服务器唯一的生产依赖是 tlock-js。一个论证是「把这个读一遍，自己核对」的项目，不该用那个来回答「我读得完这些吗？」。

所以 `server/ots.js` 直接写这个格式，而且只写需要的那部分：把一个摘要提交给公共日历服务器，写出一个 `.ots`。不做验证，不做升级，不碰比特币。那些属于读者自己的客户端，在这里做它们等于这个程序给自己的作业打分。

格式是一个魔数头、一个版本、一个哈希操作、那个摘要，然后是时间戳树，兄弟分支之间用 `0xff` 隔开。日历服务器返回的恰好就是跟在所提交摘要之后的那一段分支，所以这个文件就是一个头加上它们的回答。每个日历成为自己的一条分支：它们是互相独立的见证者，其中一个连不上不该拖累其他的。

写出一份验证不了的证明，比不写更糟——它看起来像证据但不是——所以输出是对着参考实现核对的，而不是对着我们自己对规范的理解。`python-opentimestamps` 能把它反序列化，报出我们期望的那个摘要，并找到四条 pending 的证明：

```
file hash op : OpSHA256
digest       : e57f528b0de517c006a1a40e529dd7829c1e144ff1892505ff8005ddff06f7ec
calendars    : 4
   pending at https://alice.btc.calendar.opentimestamps.org
   pending at https://bob.btc.calendar.opentimestamps.org
   pending at https://finney.calendar.eternitywall.com
   pending at https://btc.calendar.catallaxy.com
```

提交上去的是这个文件裸的摘要，不是参考客户端那样加了 nonce 的。那个客户端要隐藏自己在盖什么章；而这份名单片刻之后就会被完整公布，裸着盖章正是让读者能把 `.ots` 对着他们下载的 `snapshot.json` 验证的原因，中间不需要额外步骤。

### 秒表找出来的三个 bug

给排练计时，找出了三件没有任何断言在看的事。

**单元测试套件开始用网络了。** `publishRoll` 的默认值是那个真实的盖章器，于是每一个会执行开奖的测试都拨了四个日历：`rounds.test.js` 从一秒变成十九秒，而且它每个测试都恰好花了可疑的 1000 毫秒。盖章现在是选择加入的——`server/finalise.js` 的命令行入口传入真的那个，而一个没有主动要求的库调用方什么也拿不到。套件从 22 秒回到了 4 秒。

**一个没开镜像的部署，在每次开奖结束时要等两分钟。** `enqueue` 不管镜像有没有配置都往队列里推，而 `flush` 在没配置时立即返回——却不清空队列。于是开奖末尾的 `drain()` 一直空转到它两分钟的超时，然后返回 false，而那读起来像是失败。它一直都在那里；没有任何东西给那条路径计过时。现在被禁用的镜像什么都不入队，因为 `events/` 下的本地副本已经在磁盘上了。

**任务用轮询熬过了一个它本来就知道长度的间隔。** `finalise` 从截止时刻开始，而它在等的那个信标要到 `reveal_gap_seconds` 之后才存在。等待循环在整个这段时间里每十五秒问一次 drand，然后，等那一轮真的该到了，它还可能再错过差不多十五秒：轮询落在哪里，取决于刚才那次 OpenTimestamps 盖章花了多久。那是一段被螺在开奖末尾的随机延迟，而开奖末尾正是这个程序最不该有随机延迟的地方。

关于那一轮的时刻没有任何一处是猜的。protocol.json 把它钉死，`config.js` 推导出 `target_round_ms`，drand 按固定周期出块。所以现在第一次扑空之后直接睡到那个精确时刻，之后才开始轮询，一秒一次，因为从那时起延迟来自传播而不是来自间隔。在排练里，从信标落地到开奖完成这一段从 17 秒降到 8 秒，而且不再每次运行都不一样。一个十分钟的生产间隔此前一直在白白花掉四十次到镜像的往返。

有两个细节值得留着。这个睡眠被夹住，不会越过 `maxWaitMs`，否则一个放弃超时比自己的间隔还短的部署就会被告知得太晚。以及日志被节流成：那一轮第一次迟到时一行，此后每半分钟一行，因为在一秒一次的轮询下，一个真的卡住了的 drand 否则会用每秒一行把自己的诊断埋掉。

前两项把排练从 253 秒降到 134 秒，把 `npm run e2e` 降到 90 秒。第三项把它降到 122 秒。D14 里剩下的就是那个间隔本身——那正是这一步的全部意义——加上真正跟在信标之后的工作：十二次 tlock 解密、座位表、Pantheon 同步，以及为 `--verify` 起的第二个进程。

## 6j. 谁来开奖，以及从它底下露出来的那个 bug

服务器服务页面。`server/finalise.js` 开奖。把它们分开是 §9 的要求——任何外人能戳到的东西都不能触发、重试或改变开奖时机——而这是对的。错的是从中得出的结论：调度这个任务是别人的问题。唯一有文档的调度器是一个 systemd timer，它要求在一台组织者未必拥有的机器上有 root 权限，而且在 Windows 上根本不存在，而开发和排练正是在 Windows 上做的。

于是现实中的部署把页面服务得很好，却从不开奖。选手登录、封存数字、看着倒计时归零，然后什么都没发生——而且没有任何地方说明为什么，因为其他每一个指示灯都是绿的。

`server/schedule.js` 给了服务器一个自己的定时器。它不是一个端点：没有请求能到达它，而那个间隔是机器上一个文件里的数字，所以 §9 毫发无损。它**派生**那个任务，而不是在进程内调用 `run()`，这保住了三条比省下一个进程更值钱的性质：页面在十二次 tlock 解密期间保持响应；开奖里的一次崩溃带不走服务器；以及排练所检验的，就是 cron 会去跑的那同一条命令。`runtime.json` 里的 `run_finalise` 可以为确实有调度器的人关掉它；两者绝不能同时触发，不是因为两场开奖会给出不同答案——它们不可能——而是因为那会把提交名单盖两次章，往 Pantheon 写两次。

页面、面板和启动日志现在都会在没有任何东西开奖时说出来。那才是真正的缺陷：不是开奖有可能没被调度，而是它有可能**静默地**没被调度。

### 它暴露出来的那个时钟问题

在那一轮的精确时刻醒来、而不是一路轮询过去（第 6i 条），把一个罕见的失败变成了一个稳定复现的失败。排练先是 12 人里抽出 9 人，然后 11 人，然后又是 9 人，并且把缺的那些选手标为**被排除**，`results.json` 这么写着，排除也被公布了出去：

```
local_id 1 — It's too early to decrypt the ciphertext - decryptable at round 32098187
```

显而易见的解读是信标还没传播开。事实不是这样。tlock 从来不问信标现在是不是时候；那个检查是本地的算术，在 `tlock-js/drand/timelock-decrypter.js` 里：

```js
if (roundTime(chainInfo, roundNumber) > Date.now()) {
  throw Error(`It's too early to decrypt the ciphertext - decryptable at round ${roundNumber}`);
}
```

`roundTime` 是 `genesis_time + (round - 1) * period`，而比较的对象是**这台机器的时钟**。所以任务问的两个问题是由两个不同的时钟回答的：drand 的服务器决定信标存不存在，而本地时钟决定 tlock 肯不肯用它。一台比 drand 慢一两秒的主机，会拿到钥匙，然后被告知现在拧还太早。

这也解释了这次失败的形状，而传播解释不了：前几位选手被排除，其余的没事。每次解密要花几百毫秒，所以时钟在循环进行到一半时追了上来。

它一直是潜伏着的。十五秒的轮询意味着开奖总是在那一轮之后好几秒才运行，而那足以掩盖任何合理范围内的时钟偏差。老的节奏没有任何毛病，除了它慢到足够走运。

修法分两部分，第一部分才是真正的那个。在解密之前，任务先把自己的时钟等过去：`target_round_ms` 来自 `target_round_utc`，而那是 `tools/pick-round.js` 用同一条公式、从同一份链信息算出来的，所以它恰好就是 tlock 将要拿来比对的那个时刻。先在本地满足这个检查，再去问。

第二部分是一张网。「太早」现在抛出 `BeaconNotReadyError`，而不是和一份格式错误的密文归为一类：这一遍在第一个这样的错误处就放弃，而不是把其余的都走完，然后调用方重试——等待时是 `pollMs` 之后，或者在定时任务的下一次运行时，而它在此期间什么都不做。一轮要么被完整地抽出来，要么还没抽。

两者都保留是刻意的。一次排除是不可逆且公开的，所以产生一次排除的门槛必须是一种不可能是时序假象的失败——而那个门槛不该建立在「两份代码库之间某一条算术恒等式成立」之上。

## 6k. 等待页诚实，却无法被核验

对选手端界面的十一处改动，其中四处围绕同一个区分。

### 计数是我们的一面之词；指纹不是

等待页写着「9 / 12 已封存」，画出九枚填实的 chip。其中每一部分都是真的，而且没有一部分是可核验的：那是这台服务器对它自己数据行的计数，由这台服务器自己的 bundle 渲染出来。一个盯着它看的选手，被要求去信任的恰恰是协议其余部分致力于不去信任的那一方。

所以每个信封现在带着我们持有的那份密文的 SHA-256，默认显示前若干位，悬停或点击时拉长到完整。

显而易见的反对意见是 UI-SPEC §9：**每位选手提交了什么，在开奖之前永远不暴露。** 它不适用，而这个理由值得写下来，因为那条规则读起来就像适用。密文**本来就是公开的**，从它到达的那一刻起——§5 让它带着 commit 时间被镜像进仓库，正是为了让组织者没法在看到结果之后丢掉不合意的那一份。对一个已公开的值取摘要，透露的严格地更少。这里没有任何东西能让谁提前打开什么；能做到那件事的只有信标，而它还不存在。

省略这些摘要实际保护的是谁也没有，代价却是一个无从核验的选手。那条规则真正的内容是**明文数字**，而那一点毫发无损：§9 那句话现在用这些措辞重新表述了，既没有放宽也没有收紧。

### 空位在截止时刻改变了含义

截止之前，一个没填的信封意味着「还没交」。截止之后，同一个信封意味着「再也不会交」。它们渲染出来一模一样——一枚描边的 chip——而它们是相反的事实，其中一个仍然是可行动的。现在卡片上写明是哪一种，而此时自己尚未封存的选手会看到整页降饱和度，外加一张单独的卡：已截止、你不在这次抽签里、这不影响其他任何人，以及为什么迟交的数字不能收。最后那句话比看上去更要紧：没有它，这一页读起来像是一种惩罚，而不像是让其他所有人的提交得以安全的那样东西。

低于门槛时计数条是琥珀色而不是绿色，理由相同。在那个计数下，如果截止此刻到来，这一轮就会作废。一个绿色的条说着这件事，读起来像「没问题」。

### 一条不编造自己起点的时间轴

那两个时刻和那个轮次过去是一行小字：**封存截止 20:30 · 开奖 20:40 · drand 第 8,234,500 轮**。每一条事实都正确，它们之间的关系却看不见。它们是一个序列，相隔十分钟，其中一个还在几天之后，而那个轮次是把两者与这里谁也不经营的东西连起来的那一环。

把它画成一条轨道，立刻撞上一个不大的诚实性问题。右半段有真实的时长——`reveal_gap_seconds`——所以可以按比例画。左半段根本没有起点：提交可能两周前就开了，而服务器并不记录那是什么时候。给这条轨道一个开始日期，和一个编造的进度条是同一种谎言，只是更隐蔽一层。所以引入段画成一个 reveal gap 的长度，而在此之前游标钉在边缘，标注写着**更早开始**。

### 证据被拆成了三段

提交名单卡在一段里断言「已由四个独立日历服务器锚进比特币」，在另一段里提供两个下载，在第三段里点名 `ots verify`。读者得先想明白第二段是核验第一段的方式，再发现第三段需要装一个 Python 包。一个需要包管理器的核验步骤，就是一个不会发生的核验步骤。

三者现在是一整块，而核验是一个把两个文件拖上去的网页（opentimestamps.org，Verify）。这张卡也出现在结果页上，而它此前恰好在变得可核验的那一刻被撤走了——开奖之前那个摘要是一份承诺，开奖之后同一个文件是验证者据以重算的东西，没有任何一种读法能说它只该在前者的时候可用。

而且对选手它不再叫「名单」。那是本文档的用词。`events/snapshot.json` 是它在磁盘上的名字；选手读到的是**密文提交结果**，因为它就是那个东西。

### 原理页是生成的，不是写了两遍

`docs/seating-design.md` 从第一性原理讲清整套方案，而此前只有找到这个仓库才能读到它。现在它是应用里的一页，挂在页头一个两项菜单上，每个界面都能到达，登录页也能——一个在填数字之前决定要不要信任这套东西的选手，不该为了找答案而被迫离开。

它是构建时生成的，而不是用 JSX 重写一遍，因为选手读到的那一页和审查者审阅的那份文档必须是同一段文字。副本会漂移，而漂移掉的那一段，正是解释抽签为什么无法被操纵的那一段。

这需要一个 markdown 渲染器，而引入一个现成的会把上百个传递依赖塞进那个封存数字的 bundle 里。`tools/md-to-page.js` 只处理这份文档用到的构造，并且对别的**抛出异常**而不是把它丢掉——一个宽容的渲染器，失败模式是一段没人注意到的缺失文字。两张 mermaid 图都是简单的链，所以它们被解析成节点并画成方框和箭头；一张结果不是链的图会是一次构建错误。

中文翻译是第二份文档，不是英文的退化方案。这个应用从被写出来的那天起就说：一个不读中文的选手在每一屏都能拿到英文；159 行英文组合数学是同一个缺口指向另一个方向，而且发生在唯一一页职责就是赢得信任的地方。`test/md-to-page.test.js` 会在任一版本多出或少掉一个小节、一张图、一个示意图时失败。

### 其余的

活动名称在启动时从 Mimir 读取，现在加在应用标题和浏览器标签页前面——一个俱乐部一年办好几场，两个都写着**座位抽签**的标签页，对一个马上要提交进去的选手什么也没说。它是运营配置而不是冻结的：一个标签，它的任何可能取值都不碰种子、名册和轮次。

提交页现在显示两个时刻，既有实时倒计时也有精确时刻，按读者本机时区显示并标出偏移，下面附 UTC。在此之前，唯一一块选手还有事要做的屏幕，正是唯一一块从不说明截止时间的屏幕。

密码框加了显示切换，默认关闭。

## 6l. Ctrl+C 按下去什么也没发生

不是「慢」。是根本不退出，按多少次都一样，什么也不打印。

三行代码，每一行单独看都站得住。信号处理器调用 `server.close()`，并在它的回调里退出。`close` 要等最后一个连接结束才回调。而等待页持有的那条流按设计永远不会自己结束，放开它的是 `hub.close()`——那个函数注册在 server 自己的 `close` 事件上，也就是正在等这些流的那个事件。每一步都在等下一步，而且装上处理器这件事本身，也顺手拿掉了 Node「收到信号就退出」的默认行为，于是底下没有任何东西能接住它。

代价不是关得慢。在 Windows 上，唯一的出路是 Ctrl+Break 或者任务管理器。在 systemd 下，同一个死循环对 SIGTERM 同样成立，于是每一次 `systemctl restart` 都要干等满九十秒的 `TimeoutStopSec`，最后以 SIGKILL 收场——也就是说，每一次部署都是把 relay 从请求中间劈掉，而不是让它停下来；而那个 unit 文件里关于「不要打断开奖」的仔细注释，描述的是一件并没有在发生的事。

现在的顺序是：先流，再套接字，最后才是等待。`hub.close()` 结束那些响应；`closeIdleConnections()` 丢掉浏览器随手留下的那条备用 keep-alive 套接字——它把 close 卡住的力度，和一个正在进行的请求完全一样；到这一步才真的没有什么好等了。有选手挂着时实测 15 毫秒，并且在真实程序上用一次真实的控制台 Ctrl+C 复核过：流结束了，客户端看到它结束了，进程没了。三秒之后还挂着的东西会被丢掉并在日志里说一声，因为一个站在终端前按 Ctrl+C 的人并没有要求等它。再按第二次立刻退出——前提是第一次在他看来不像起了作用。

开奖子进程仍然被刻意放着不管。一个只发布了一半的轮次，比一个没人管的进程更糟。

这个测试值得记一笔的是它失败的方式：如果 bug 回来了，它不会失败，它会挂住。那正是这个 bug 本身。一直都在的那个 SSE 测试从来没抓到它，因为它在关闭之前先取消了 reader，而那恰恰是一个坐在等待页上的选手永远不会做的事。
