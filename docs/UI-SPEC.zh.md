# 选手端界面规范

> [English](UI-SPEC.md) · 简体中文

一页，一条连续的流程。选手登录，被一路带着走完抽签，最后停在座位表上。**抽签之上没有 tab 栏**——下面那六种情形是同一段旅程的各个阶段，不是可以随意浏览的分区。应用知道抽签处在哪个阶段，就显示那个阶段；更早的阶段在它后面，不在它旁边。

只有一个去处不是阶段：**原理**，也就是对这场抽签的说明，从页头一个两项菜单进入，每个界面都有（§10）。它在旅程**旁边**，不在旅程**里面**——打开它不会动到阶段状态机，回来时落在抽签这期间变成的样子上。一个想在填数字之前弄明白凭什么信任这套东西的选手，不应该被迫离开应用才能找到答案。

## 1. 设计原则

- **一次只讲一件事。** 每个阶段恰好有一个焦点元素。辅助信息在尺寸、字重和颜色上都是次要的，绝不与之竞争。
- **动的是应用，不是选手。** 提交之后，选手不需要回来、不需要刷新、不需要点任何东西就能往下走。阶段变化通过 SSE 到达并自己动画进场。
- **动效承载意义。** 每一个动画都应当编码协议里某件真实的事——封存、等待、打开——而不是装饰。如果一个动画删掉也不损失信息，那它就太长了。
- **诚实地等待。** 等待阶段显示真实状态：真正的 drand 轮次、真实的计数、由服务器时间驱动的倒计时。没有假的进度条。
- **尊重 `prefers-reduced-motion`。** 每一次转场都有交叉淡入的退化方案；没有任何重要信息只靠动作传达。

建议技术栈：任意现代 SPA 框架，单一路由，一个状态机（`xstate` 或者朴素的 reducer）驱动一个在各阶段之间交叉淡入的 `<main>`。布局转场用共享元素库（Framer Motion 的 `layoutId` 或 View Transitions API）效果最好。以上都不是强制的。

## 2. 阶段状态机

```
signin ──▶ submit ──▶ submitted ──▶ waiting ──┬─▶ revealing ──▶ result
                                              └─▶ void
```

阶段是**推导**出来的，客户端从不存储：`GET /api/status` 给出抽签的 phase，`GET /api/me` 说明这位选手是否已提交。截止之后才登录的选手会直接落在 `waiting`、`result` 或 `void` 上——流程对所有人都一样，只是入口不同。

| 阶段 | 何时显示 |
|---|---|
| `signin` | 没有会话 |
| `submit` | phase 为 `open`，且这位选手尚未提交 |
| `submitted` | 他自己的提交被接受的那一刻（瞬态，约 2.5 秒，然后转 `waiting`） |
| `waiting` | phase 为 `open` 且已提交，或 phase 为 `awaiting_round` |
| `revealing` | phase 为 `revealing`（瞬态，由开奖动画驱动） |
| `void` | phase 为 `void` |
| `result` | phase 为 `done` |

## 3. 登录

一张居中的卡片：活动名称、一行说明（「用你的 Pantheon 账号登录，参加本次座位抽签」）、邮箱、密码、提交。

Pantheon 给出活动名称时，标题里要带上它——「2026 春季公开赛座位抽签」，而不是光秃秃的「座位抽签」。一个俱乐部一年办好几场，选手手上可能同时开着两个页面；一个和上个月那场分辨不出来的页面，就是人们会误提交进去的页面。这个名字在启动时从 Mimir 读取，且不冻结：它是个标签，任何取值都不会改变谁坐在哪里（`PROTOCOL.zh.md` §4.2）。

每个输入框由框内的图标标注——信封、挂锁——而不是框上方的文字。文字仍留在标记里，供屏幕阅读器使用。两个已被反复习得的图形，说清了原本占掉卡片两行高度的内容。

密码框带一个显示切换，默认关闭，位于框内右端。在嘈杂的俱乐部里对着手机盲打密码，正是「试三次失败」演变成「Pantheon 把我忘了」的方式。

Stub 模式只替换输入框，别的都不换：同一张卡片、同一套外壳、同样的节奏。这就是选手在生产环境里会看到的页面，而在开发中诚实地审视它的唯一办法，就是让它是同一个页面。

浏览器直接向 Pantheon 认证，只把返回的 token 对发给我们的后端（见 `PANTHEON-INTEGRATION.zh.md` §2）。两条失败提示，必须清晰区分、不可混淆：

- 凭证错误 → 「Pantheon 不认识这个邮箱和密码。」
- 账号有效但不在这场活动里 → 「这个账号没有报名本次活动，无法参加抽签。」

第二条是正常结果，不是错误状态——按信息来排版，不要按警报。

登录还可能以别的方式失败，每一种都有自己的一句话，并在下面附上技术行（HTTP 状态码，以及有的话 Twirp code）：浏览器连不上 Frey、Pantheon 地址配错、Pantheon 出错、连不上这台服务器、这台服务器的限流、在明文 http 上被拒绝、浏览器没有保存会话、页面认不出来的回答。规则只有一条：除非 Frey 或者这台服务器对 Frey token 的复查拒绝了凭证，否则任何失败都不显示成「密码错误」。登录之后，页面会先把会话读回来再往下走，所以被浏览器丢掉的 cookie 在这里就会报出来，而不是等到提交的时候。

## 4. 提交数字

整个应用的焦点。一个大号数字输入框，字号大到让人觉得这件事有分量（48–64 px），配上：

- **范围** `0 … 255`，实时校验。行内提示：「0 到 255 之间的任意整数——幸运数字、生日，都行」。
- **一个「帮我随机选一个」按钮**，用 `crypto.getRandomValues`，数字滚动着落定。这是给不想自己挑的人的便利；输入框初始为空，自己打一个数字才是预期路径。
- **一句为什么**，不要更多：「你的数字在你的浏览器里封存，在抽签开启之前任何人都读不到——包括我们。」
- **提交**是屏幕上唯一的主操作。

提交时客户端构造 `{user_input, client_nonce, client_timestamp}`——nonce 是 `crypto.getRandomValues` 给的 16 字节——用 tlock 把它封给冻结的 `protocol.json` 里那条链和那一轮（访问该链所用的端点来自 `/api/status`，因为端点不冻结——`PROTOCOL.zh.md` §4.2），然后只发送密文。nonce 是静默生成的；不管选手打了什么数字，正是它保证了这份贡献是均匀随机的，而它会在开奖时和其他一切一起揭示，所以选手仍然能核验自己的数字确实进去了。要显示一个简短的行内工作状态——封存是一次真实计算，如果它不是瞬间完成的，就不该看起来像瞬间完成。

不要提供修改或撤回的入口。提交按设计就是终局的；这句话要说在按钮**之前**，不是之后。

**两个时刻都要在这一屏上，剩余时间放在它们上面。** 卡片顶部、标题之上一条带子，先说还剩多久——大号、居中，因为这是这一屏上唯一一个选手不必自己做减法就能据以行动的数字。它下面隔一条细线是两个精确时刻：抽签截止，以及开奖，都按读者本机时区显示并标出偏移，drand 轮次以小字放在两者之下。它们是两个不同的时刻，相隔 `reveal_gap_seconds`（`PROTOCOL.zh.md` §9），而在此之前，这唯一一块选手还有事要做的屏幕上，两者一个都没出现过。进入最后半小时后，这条带子转为警示色并说明这一点。

倒计时的字号比数字输入框小一档，§1 要求的唯一焦点因此仍然落在输入框上。不再重述 UTC：每个时刻本身已经带了偏移，再用 UTC 说一遍，等于在这块最不该有多余东西的屏幕上把同一件事说了两次。标题和它所指的输入框之间不放任何东西——带子和作废提示都因此放在问候语之上。

这条带子只有一套配色，取自它当前的状态：还有时间时是主色，进入最后半小时是警示色，标签和时刻也一样。它过去是嵌在面板里的一块页面底色，强调文字用的是纯墨色，于是警示状态把底色刷成琥珀，却把两个时刻留成压在上面的冷黑。绿转琥珀正是提交进度条已经在用的「稳了」和「还不稳」，所以这次变色是信息，不是装饰。

## 5. 已提交，以及等待

**已提交**是一句简短的确认，不是一页：数字卡片折起封住——一个封信封的动作——一个对勾在它下面画出来，配文「已封存。接下来不需要你做任何事了。」约 2.5 秒后它自行让位给 `waiting`。它和它所替换的提交卡片同宽：封存是就地发生的，这一刻卡片如果换了宽度，读起来是页面在跳，而不是同一张卡片合上。

**等待**是大多数选手真正会停留的阶段，可能停上好几天，所以它必须真的有信息量：

- **倒计时**指向目标轮次，作为视觉锚点——一个圆环或一个大钟，由 `/api/status` 里的 `server_time_utc` 驱动（客户端与服务器的偏差在加载时测一次），因此永不漂移。
- **一条时间轴**，而不是一行小字。两个固定时刻是一个**序列**——提交关闭，`reveal_gap_seconds` 之后能打开它们的信标才存在——而 drand 轮次是把两者与这里谁也不经营的东西连起来的那一环。所以：一条轨道，上面标出截止和开奖，一个「现在」的游标，每个时刻都用本地时间加偏移标注，下面把当前轮次和目标轮次排成大字并标出两者的距离。左半段没有诚实的起点（提交可能两周前就开了），所以画成一个 reveal gap 的引入段，在此之前游标钉在边缘并标注说明。给这条轨道编一个开始日期，和编一个进度条是同一种谎言。
- **十二个信封**——每位选手一张卡片，上面是我们持有的那份密文的 SHA-256，默认显示前若干位，点击或轻触时展开到完整，再点一次收起；悬停什么也不做——多出来的那些字符来自只有点击才会设置的组件状态，所以一条在悬停时把框撑宽的样式规则，撑开的是一个空框，撑完之后显示的还是那十位。谁封存了是公开的；他封存了**什么**不公开，而密文的摘要两者都不是：密文本身在到达时就已公开（`PROTOCOL.zh.md` §5），能打开它的只有信标。十二行计数是我们的一面之词；一个选手能留存并事后核对的指纹不是。选手自己那张卡要标出来。
- **门槛标记**画在进度条上：8 这个阈值标在轨道上，选手一眼就能看出抽签是否已经稳了。低于该阈值时填充是琥珀色而不是绿色——在这个计数下，如果截止此刻到来这一轮就会作废，而一个绿色的条说着这件事，读起来像「没问题」。
- **截止之后，一个空位不再意味着「还没交」，而是意味着「再也不会交」。** 它们在一排 chip 里长得一模一样，含义却相反，所以卡片上要写明是哪一种。此时自己尚未封存的选手会看到整页降饱和度，外加一张单独的卡：提交已截止、你不在这次抽签里、这不影响其他任何人，以及为什么迟交的数字不能收。
- **drand 状态**——信标是否在推进，以及最近一次确认是什么时候。轮次数字本身放在时间轴里；如果信标不新了，就直白说出来，不要藏着。
- **倒计时归零之后**，是三种状态而不是一种。服务器从不开奖——开奖由一个独立任务按定时器执行——所以页面必须区分「结果还有一分钟」和「根本没人在算」。`status.draw.overdue` 为假时它说**开奖中**；一旦为真，它就说开奖没有运行、已经晚了多久、结果在截止时就已固定且无法被影响，以及请联系组织者。一个永远转下去的动画，和一个编造的进度条是同一种谎言。

这里的一切都通过 SSE 更新。如果流断了，退化为轮询 `/api/status`，并显示一条低调的「正在重连」提示。间隔取自 status 载荷里的 `status_poll_interval_ms`，默认 15 秒。

## 6. 开奖

到截止时刻且达到门槛，抽签自行运行，等待视图转场进入它。这段序列应当读起来是一个连贯的想法——封着的东西打开、合并、落定成一个顺序：

1. **信标落地。** drand 元素从「等待第 N 轮」解析为真实的轮次值。
2. **信封打开**，快速错落地一个接一个，各自露出那位选手的数字。
3. **数字折叠在一起**成为那唯一的种子——一次可视化的异或，多个值坍缩成一个。
4. **种子洗动名字。** 十二枚名字 chip 散开，落定到模板的十二个位置上。
5. **座位表在下方浮现**，浏览器变为可交互。

整段预算约 6–8 秒，点击可跳过，对在它已经发生之后才到达的选手完全短路——他们看到的是成品结果，不是回放。在 `prefers-reduced-motion` 下，第 2–4 步合并为一次交叉淡入，同样的信息以文字陈述。

**如果没达到门槛**，应用改去 `void`：一页平静、不指责的说明，写明十二人中封存数字的不足八人、按开始之前就定下的规则本轮作废、将公布新日期并且**所有人**都要重新提交。显示达到的计数和阈值。没有倒计时，没有重试按钮——这里确实没有选手能做的事。

## 7. 结果：先说怎么办，再给座位表

结果阶段开头给的是选手**接下来**需要的东西，在他要浏览的数据之前：

- 他自己第 1 轮的桌号和座位，一句话说清；
- 开赛时间和地点，如果配置了的话；
- 一行确认座位表已同步到 Pantheon，让他知道手机端看到的会和这里一致；
- 一个低调的链接，说明这次抽签怎样被独立复核。它必须先说清文件从哪里来，并且照着写的顺序能跑通。它此前一个仓库都没提；而它随后让读者去核验的那两个文件是开奖时写的，发生在冻结之后：它们在默认分支上而不在 tag 里，所以 checkout tag 会把它们删掉，验证随后失败在「文件不存在」上，而不是失败在抽签本身。仓库来自状态里的 `mirror_repo`，tag 来自结果里的 `generate_script_ref`，两者都绝不兜底成某个名字——一个凭空写出 tag 的页面，是在让十二个人去 checkout 一个不存在的东西；
- 封存的密文、它们的指纹和时间戳证明，可下载——和等待期间同一张卡。只在开奖前提供它们，等于在它恰好变得可核验的那一刻把证据撤走了。

下面是座位表浏览器。

### 座位表浏览器

一块画布，三种视角，没有 tab——视角跟着选择走：

- **什么都没选——所有人。** 完整网格：十二行（选手）× 十一列（轮次），每格按桌子着色并带上风位字母。这就是 `seating-design.zh.md` 里那张模板图，换成真名。
- **选中一位选手**（点他那一行，或者点应用里任何地方的他的名字）。他那一行浮起，其余退后。网格旁边打开一个详情面板，展示这位选手的整届赛事：逐轮列出在哪张桌、什么风位、另外三家是谁——三家各自标注为**你的上家**、**你的下家**或**对家**。
- **选中一轮**（点列头）。网格暗下只留那一列，该轮的三张桌子渲染成真正的桌子——四个座位按东南西北摆开、名字就位，画成选手进屋后会看到的样子。

选择是互斥的，并且随时可退出（点背景，或按 Escape）。URL 应当带上选择（`?player=…`、`?round=…`），这样选手可以把自己赛程的链接发给别人。

### 逐人统计

详情面板还带上那些让公平性可见的数字：

- **风位**——东南西北的次数。永远是 `{3,3,3,2}`；要说出来，好让选手知道这是构造出来的而不是运气。
- **桌次**——在三张桌子上各自的次数。九位选手是 `{4,4,3}`，三位是 `{5,3,3}`；如果这位选手是那三位之一，就把它点明为那一处不可避免的不平衡，并链接到说明。
- **对手**——每位其他选手一行：同桌次数（永远是 3），以及这三次相遇如何拆分为**对坐**（永远是 1）、**他在你上家**、**你在他上家**。
- **完美配对**——这位选手的十一对关系里有多少是平衡的，即两个方向各一次。在对手列表里标出不平衡的那些，因为整份赛程里只剩那些不对称。

以上全部由座位表推导而来；`GET /api/result` 应当把它们预先算好返回，客户端不做任何组合计算。

### 证据卡

显示两次：等待期间，此时指纹是一份承诺，十二个人被请求互相比对，而谁也打不开任何东西；以及结果页上，此时同一个文件是验证者据以重算的东西。是一整块，不是三块：「已锚定进比特币」这个声明、支撑它的文件、以及核验它的方法，三者属于一起——拆开之后，页面在一段里断言某件事，在另一段里提供一个下载，把「后者就是核验前者的方式」这层关系留给读者自己想明白。

核验是一个把两个文件拖上去的网页（[opentimestamps.org](https://opentimestamps.org)，Verify），不是命令行。一个必须先装一个 Python 包才能核验抽签的选手，不会去核验抽签。

复制按钮复制的是屏幕上那十六个字符，不是它背后的完整摘要。这是页面请求十二个人互相念给对方听的唯一一个值，所以粘贴出去的东西必须就是别人正在看的东西；把六十四位全发过去让比对更难而不是更强，因为收到的人还得在一堵十六进制里找出前十六位。完整摘要仍然只隔一次悬停，要重算而不是要肉眼比对的人可以从 `snapshot.json` 里取。这个控件是一个图标：一个词放在 30px 的值旁边，会被读成那个值的一部分。

把这个文件叫成它本来的样子——大家提交的密文——而不是「名单」。`snapshot.json` 是它在磁盘上和归档里的名字；那个名字不必是选手读到的措辞。


### 决赛轮

带第十二轮的赛事（PROTOCOL.zh.md §11）会在结果页上放三样东西，其中第一样在那一轮抽出来的**好几周之前**就出现了。

**封存卡片**，它是存证卡片的兄弟，而且刻意做成它的孪生兄弟，连 class 都一样。两者提出的是同一个请求——这里有一串短字符串，趁着还没有人知道它会打开什么，跟另外十一个人核对一下——而两张长得像不同机制的卡片，会让读者以为它们真是不同的机制。它显示封存文件的指纹、将要抽风位的那一轮 drand 及其预计出块时间，以及**三张桌子**，桌次已经定了，因为是名次定的。还没有人知道的是谁坐东家。「核对指纹」这个请求只在已锁定、未抽签时显示：抽完之后，同一串摘要就只是组织者念给你听的一个数字。

**大标题会移动。** 在第 1 轮还是下一件要去做的事时显示第 1 轮；决赛轮一旦存在就显示决赛轮。一个几周之后还在宣布第 1 轮的页面，会恰好有一句话——而且是最大的那句——讲的是过去。

**第二个验算区块**，放在第一个旁边而不是并进去。现在有两次抽签要核验，核验方式相同，而且各自都指向一份第二实现。

逐人统计里有三句话，对十一轮是真的，对十二轮是假的，而这一节的存在就是为了标出这个坑。风位按**打过的全部轮次**统计，因为那正是决赛轮要纠正的那个量。桌次和配对仍然限定在**前十一轮**，因为 `{4,4,3}` 和「66 对里 11 对」是模板的性质，由 `tools/verify_template.py` 证明，而且是邀请选手自己去跑的；一个悄悄改变了含义的数字，会和页面自己指向的那个验证器相矛盾。

最后是 4-3-3-2 而不是 3-3-3-3 的人，会被告知他当时真实的概率——*m* 分之一，*m* 是他那桌有多少人缺同一门风——以及规则为什么这么设计。不是「你运气不好」。这个设计把「每门风各三次」的人数最大化，代价就是缺同一门风的人要分享同一个座位。把这个数字说出来，才让公平性的说法是可核验的，而不是安慰性的。
### 当座位上的名字不是实际打的那个人

座位可能在比赛中途换人（PROTOCOL.zh.md §11.6）。冻结花名册里写的仍然是最初坐在那里的人，而一个只显示那个名字的页面，就是在关于「谁坐在那张桌子旁」说一件假的事——而且看上去完全正确。

所以在封存证据卡上，换过人的座位**标的是实际打完的那个人**，带一个标记，并在下方列出他从第几轮接手、以及允许此事的联赛规则。一个座位可能换过不止一次；标签用的是最后那位，因为他才是坐在桌旁的人，而列表给出整条链，因为「这十一场是谁打的」不是最后一个名字能回答的。

卡上还要用两种语言写明：这次替补**没有改变抽签的任何一点**——座位保留了原来的 Pantheon 注册位，所以名次表仍是一人一行，桌次与没换人时一致，种子里没有一个字节发生变化。这个断言正是一次替补可以声明得晚而不会变成杠杆的理由，也是卡上唯一一件读者无法自己核实的事。如果它没写在那里，那就等于没有做出这个断言。

没有替补的时候什么都不显示：没有标题，也没有空列表。正常情况就是没人退赛，而一个永久存在的空区块只会让十二个人猜它是什么意思。

页面从 `/api/result` 取这份记录，而一旦锁定文件存在，它提供的是**锁定文件里的那一份**而不是当前的活文件——这样页面绝不会显示出一份与「请大家核对的那个指纹」下不一致的记录。

## 9. 不可协商的几条

- 没有需要选手手动导航过去的阶段，页头也不能有任何把抽签自身的阶段变成分区的东西。那唯一一个不是阶段的菜单项通向抽签之外，并原样带你回来。
- 等待视图绝不编造它观察不到的进度。
- 每位选手提交了什么，在开奖之前永远不暴露——不在端点里，不在载荷里，也不在调试头里。只有**是否**提交，以及那个封存信封的指纹，而指纹是对一份本已公开的密文取的摘要，打不开任何东西。
- 开奖动画可跳过，并且从不阻挡访问结果。
- 一切都要在手机上可读：12×11 的网格需要经过考虑的小屏方案（横向滚动加固定姓名列可以；挤成一团看不清不行）。

## 10. 原理页

一页，构建时从 `docs/seating-design.md` 和它的中文版生成——不在客户端里再写一遍。选手读到的那一页和审查者审阅的那份文档必须是同一段文字；副本会漂移，而漂移掉的那一段，正是解释抽签为什么无法被操纵的那一段。

每个界面的页头都能到达，双向可走，Escape 可退出。它带一份目录，会指出读者当前在哪一节，还有文档的插图和示意图。返回时抽签停在原处。

两种语言都是同一份文档的完整翻译，`test/md-to-page.test.js` 会在任一版本多出或少掉一个小节、一张图、一个示意图时失败。
